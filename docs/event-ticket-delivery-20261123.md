# Legal Night Jazz 2: выдача билетов, 23.11.2026

## Причина и исправление

В исходном коде после подтверждения оплаты вызывалась только отправка письма; Telegram получал уведомление администратора, но не билет покупателя. Результат доставки не сохранялся. После ошибки SMTP повторное платёжное уведомление пропускало уже оплаченную регистрацию. Ошибка генерации PDF также могла завершиться письмом без билета.

Теперь запись оплаты и постановка выдачи билета в очередь сохраняются вместе. Почта и Telegram работают независимо. Фоновый обработчик проверяет очередь каждые 15 секунд. Однозначно не выполненная отправка повторяется с задержкой от 30 секунд до часа; успешная отправка повторно не выполняется. После ошибки формирования PDF письмо остаётся в очереди. Подтверждение оплаты по `order_id=ev-N` также распознаётся; противоречащие номера регистрации не засчитываются.

SMTP после DATA может оборваться уже после принятия письма. Такой исход или прерванная отправка сохраняется как `uncertain` для проверки, без автоматического повторения. Положительный ответ SMTP означает принятие почтовым сервером, но не гарантирует попадание во «Входящие».

Telegram требует запуска бота покупателем. Ссылка «Получить билет в Telegram» есть в письме и на странице успешной оплаты. Она связывает непредсказуемый токен билета с приватным Telegram ID. Сопоставления по одному `@username` нет. Неоплаченному билету PDF не выдаётся.

## Установка и проверка на сервере

Из подготовленного checkout с этим изменением:

```bash
node scripts/install-event-ticket-delivery.mjs
```

Установщик определяет активный runtime единственного онлайн-процесса `legalcareerist-api` через PM2. Перед изменением кода проверяет известные версии модулей, синтаксис и формирование реального PDF на зависимостях сервера. Выполняет только чтение `getMe`/`getWebhookInfo` и `SMTP.verify()` — без тестовых писем и сообщений покупателям. Не удаляет внешний вебхук Telegram и не меняет настройки почты.

Приватная резервная копия кода и отчёты находятся в `/root/legalcareerist-bot-backups/event-ticket-20261123-*`. Изменения ограничены обработчиками билетов и зависимостями генератора. Существующие шаблоны не перезаписываются. `.env`, тарифы и финансовая история не заменяются. При неуспешном запуске восстанавливается прежний код, но новые данные платежей после перезапуска не откатываются.

Успешное завершение: `EVENT_TICKET_DELIVERY_INSTALLED` и `codeVersion: 1`. Отдельно проверить `smtp.verified`, `botReady`, `botUpdatesReady`. `DELIVERY_CONFIGURATION_REQUIRED` означает, что установка кода завершена, но подключение SMTP или получение обновлений ботом требует исправления. `smtp.errorCode: EAUTH` обычно означает ошибку SMTP-авторизации. В отчёте нет паролей, токенов и контактов покупателей.

Новая версия `/api/health` возвращает `eventTicketDelivery: 1`. Для новой регистрации проверить два факта: статус «Оплатил» и состояния `ticketDelivery.email` / `ticketDelivery.telegram`. Статус `waiting` в Telegram до запуска бота ожидаем.

## Уже оплаченные билеты

Без истории отправки нельзя достоверно отличить получившего билет от не получившего. Поэтому установщик выводит номера старых оплаченных регистраций в `paidWithoutDeliveryHistory`, но не рассылает им билеты автоматически.

Для конкретных покупателей, сообщивших о проблеме, при установке можно явно указать номера регистраций:

```bash
node scripts/install-event-ticket-delivery.mjs --retry-paid 41,42
```

`41,42` — только пример; подставить проверенные номера регистраций. Скрипт принимает лишь существующие оплаченные регистрации Jazz 2, не меняет их оплату, сумму или номер платежа. Почта ставится на повторную отправку; уже подтверждённая доставка в Telegram сохраняется. Без привязанного Telegram аккаунта билет дождётся запуска бота. Повторное использование `--retry-paid` повторно запрашивает отправку, поэтому запускать его только для действительно не полученных билетов.

После установки адресную повторную отправку письма также можно запустить существующей кнопкой «🎟 Выслать билет на почту» в карточке регистрации администратора. `signedPaymentNotCredited` в отчёте — повод отдельно сверить исходный платёж; установщик не создаёт оплаты по догадке.

## Проверки без реальных рассылок

- `node --test server/tests/event-ticket-delivery.test.mjs`: отдельные подтверждения каналов, перезапуск, сбои, параллельность и запрет выдачи неоплаченных билетов.
- `node server/tests/http-reliability.mjs --event-tickets`: реальные HTTP-обработчики, подписанные тестовые платежи, формирование PDF, получение в боте, повторы и ошибочные привязки. SMTP и Telegram заменены тестовыми ответами.
- `node scripts/tests/event-ticket-install.mjs`: установка, повторный запуск, неизвестный код, SMTP-ошибка, откат, сохранение платежа во время неудачного запуска.
- `node scripts/tests/event-fixed-checkout.mjs`, `node server/tests/http-reliability.mjs`, `node server/tests/http-reliability.mjs --no-payment-keys`: исходная оплата билетов и подписок, отсутствие обхода проверки подписи.
- `npm run build`: сборка страницы с получением билета в Telegram.

Состояние SMTP и фактическая доставка на Timeweb из среды разработки не подтверждены: доступ к серверу и рабочим ключам отсутствует. Установщик выдаёт отдельный отчёт именно с сервера.
