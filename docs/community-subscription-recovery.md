# Персональное восстановление завершённых подписок

Это отдельный операторский сценарий для ранее плативших резидентов. Публичный тариф 690 ₽ не меняется, новые планы в Prodamus не создаются. Данные конкретных получателей передаются через stdin на сервере, не сохраняются в публичном репозитории.

## Порядок работы

1. Установить пакет с поддержкой восстановления. Клиент проверяет фактически работающую версию API и совпадение исходных файлов с пакетом.
2. Оператор передаёт идентификатор кампании и точные Telegram ID, имена, телефоны, прежние планы/суммы/сроки и дату завершения в Prodamus.
3. `providerCompleted: true` означает, что владелец уже проверил завершение в кабинете Prodamus. Это ручное подтверждение оператора, а не результат запроса к API. В таком случае повторная отмена в Prodamus не выполняется. Без этого признака требуется успешный ответ провайдера на отключение прежнего плана.
4. Перед отправкой проверяется числовой Telegram ID через `getChat`. При уже учтённой новой оплате после даты снимка приглашение пропускается. Ники не являются ключом адресации.
5. Внутри процесса API создаётся отдельная неоплаченная карточка восстановления. Исторические платежи и даты не перезаписываются. Из отдельного консольного процесса финансовые JSON не изменяются.
6. Ранее оплаченные карточки получают обычное единое окно дополнительного доступа — по умолчанию четыре суток от подготовки восстановления. Окно хранится отдельно от оплаченного срока, не перезапускается повторной командой и не записывается как выручка. Защита включается до внешних действий, чтобы параллельная задача исключения не закрыла доступ посреди подготовки.
7. Формируется подписанная ссылка на прежний план. `customer_extra` содержит непрозрачный маркер новой карточки; в ссылке также передаётся числовой Telegram ID. Закрытые публичные 3/6 месяцев доступны в этом операторском сценарии только по согласованным историческим условиям.
8. Отправляется одно личное сообщение с причиной остановки, прежней стоимостью и кнопкой оплаты. Само сообщение, открытие ссылки и операторское подтверждение завершения не засчитывают новую оплату.

## Что происходит после оплаты

- Требуется подлинное подписанное уведомление Prodamus со статусом `success`.
- Новая карточка сопоставляется с согласованным планом и получателем до поиска по старому профилю. Это работает и при повторном использовании Prodamus прежнего ID профиля/номера платежа.
- Начало восстановленной подписки — время новой успешной оплаты из Prodamus. Дата самой первой исторической оплаты остаётся в старой карточке.
- Продолжительность берётся из условий плана, дата следующего списания — из Prodamus либо рассчитывается при отсутствии корректной даты. Несоответствие расписания новому периоду и отсутствие достоверного времени оплаты отмечаются для проверки администратором.
- Регулярная цена берётся из согласованных условий восстановления. Фактически полученная сумма записывается отдельно. Например, повторная скидочная первая оплата 350 ₽ не превращает регулярные 500 ₽ в вечные 350 ₽; расхождение требует проверки, деньги не подменяются.
- Обновляются метки резидента, тарифа, цены и дата начала новой подписки; снимается метка ожидания восстановления.
- Если человек уже в чате, подтверждается фактическое участие. Если его нет, выдаётся ссылка на заявку; бот проверяет оплаченный доступ и одобряет вступление. Принудительное добавление через Telegram невозможно.
- Следующие платежи привязываются к новой карточке, даже если профиль Prodamus остался прежним. Старые дубликаты платежей не создают новую выручку и не меняют новый период.

## Защита отправки

- Один идентификатор кампании и получатель — одно приглашение. При повторном запуске уже доставленное сообщение пропускается.
- Состояние `sending` записывается до обращения к Telegram. Таймаут после возможной отправки даёт `delivery_unknown`: автоматически повторять такое сообщение нельзя. Нужно проверить личный чат.
- Подтверждённый отказ Telegram (`send_failed`) можно повторить после устранения причины. Уже подготовленная ссылка и исходный срок дополнительного доступа сохраняются.
- Подтверждённая новая оплата даёт `already_paid`; по старому снимку повторный платёж не предлагается.
- Кампания выполняется через внутренний API с подписью отдельного назначения, свежим временем и nonce. Подпись платёжного вебхука не подходит для запуска рассылки. Секреты остаются на сервере и не выводятся.

## Команда оператора

В рабочей папке сайта запускается `node --env-file=server/.env /путь-к-пакету/scripts/recover-community-subscriptions.mjs --send`. JSON передаётся на stdin. Без `--send` выполняется предварительный просмотр без отмен, создания карточек и отправки.

Пример структуры с вымышленными данными:

```json
{
  "campaignId": "example-recovery-20261103",
  "recipients": [{
    "telegramId": "900000021",
    "name": "Получатель",
    "phone": "+79000000221",
    "planId": "2611880",
    "amount": 500,
    "months": 1,
    "endedAt": "2026-11-01T15:00:00+03:00",
    "providerCompleted": true
  }]
}
```

Перед запуском нужно установить соответствующий пакет, чтобы реально работающий обработчик платежей знал новый маркер. После отправки в итоговом JSON должны быть `sent` либо подтверждённые причины пропуска. Это подтверждает результат Telegram API; оно не доказывает, что пользователь прочитал сообщение или оплатил.
